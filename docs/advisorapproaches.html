TextMate · Advisor Redesign · 7 July 2026

Raising the rule-violation detection rate

The advisor misses violations, and re-running it on the same text keeps finding new ones. Three architectures to fix that — compared, with a recommendation, an answer to the interacting-number-rules question, and the documentation of the new evaluation harness.

Branch claude/advisor-detection-improvement-bsftel · model Gemma (~30B) on self-hosted vLLM · 65 rules across bundeskanzlei and merkblatt_behoerdenbriefe

Diagnosis

Why one run finds so little

Today each request is thirteen sequential LLM calls: “here is the whole text and 5 rules — list all violations.” Open-ended list generation is where LLMs systematically under-produce: after two or three findings, ending the list is the most probable continuation, so each sample stops at a different point. That is why repeated runs keep surfacing new findings — the union of N runs is much closer to the truth than any single run, but today that variance is thrown away. Three further losses compound it: the same fixed batches hit the same positional attention bias every run, a single 60-second timeout silently drops the tail batches, and violations whose quoted snippet can't be located in the text are dropped with only a log line.

Options

Three approaches

All three assume the constraints agreed in the design interview: recall first (dismissible false flags beat misses), parallel calls against your own vLLM are fine, and a small second model can be deployed for cheap judge calls.

A

Tuned single pass

Keep one sample per rule batch, but fix everything around it: checklist output that forces a per-rule verdict, smaller batches (3–4 rules), paragraph-window chunking for scanning-type rules, parallel execution with per-call timeouts, and a recall-first prompt demanding every occurrence.

Pros

  • Cheapest: roughly today's call count, run in parallel — fastest wall-clock of the three
  • No new pipeline stages; ships in days
  • Checklist format alone removes the “list ended early” failure mode for rule coverage

Cons

  • Still one sample — run-to-run instability remains; the union-recall headroom stays unharvested
  • No precision mechanism, so the prompt must stay conservative, capping recall
  • Occurrence-level exhaustiveness still rests on a ~30B model's attention

Choose if GPU budget collapses or as the guaranteed-win subset — every fix here is also part of B.

B Drafted plan

Ensemble → vote → verify

Everything in A, plus: K samples per (rule-batch × chunk) cell at temperature ≈ 0.8 with shuffled rule order, all in parallel. Candidates are clustered by (rule, overlapping span); high-agreement clusters are accepted, low-agreement ones go to a binary LLM judge (“does this snippet violate this rule?”) on the small model. Violations stream out only once final, tagged with confidence.

Pros

  • Directly harvests the observed “N runs ∪ results ≫ 1 run” effect — the biggest known recall reserve
  • Voting + verifier decouples recall from precision: the detector can be aggressive because the judge restores precision
  • Stable, reproducible-ish results; agreement doubles as a confidence signal for the UI
  • No rule-data changes needed — works with the rule JSONs as they are

Cons

  • 80–150 LLM calls per check — needs the parallel vLLM headroom it was designed for
  • More moving parts: clustering, thresholds (K, agreement) to tune empirically
  • Recall ceiling is still the model's: what zero of K samples ever notice stays invisible

Choose as the core pipeline — highest expected win per effort, no schema or contract prerequisites.

C

Trigger–judge hybrid

Mechanical rules get a deterministic trigger (regex / small parser, tuned for 100% recall on the surface pattern) that finds every candidate span; a focused LLM judge call then decides “violation or exception?” per span, with the interacting sibling rules in context. Exception-free rules (every ß is wrong) skip the judge. Semantic rules stay fully LLM-checked.

Pros

  • Deterministic recall for ~⅓ of the bundeskanzlei rules — no occurrence is ever skimmed past
  • Near-zero LLM cost for decided rules; one short judge call per candidate otherwise
  • Robust to rule interactions and Sonderregeln — the judge owns the exceptions (see below)
  • Frees the whole LLM budget for the semantic rules that need it

Cons

  • Only covers rules with a surface pattern; semantic rules gain nothing
  • Checker specs must be authored, reviewed, and maintained per rule (offline LLM-drafted, human-approved)
  • A wrong trigger is a systematic error — review is mandatory, and each checker needs eval cases

Choose as the add-on for mechanical rules once B is measured — it composes with B rather than replacing it.

Recommendation

B now, C on top, A inside both

These are not rival endpoints: A's fixes are the first half of B, and C bolts onto B's front as its stage-1. The recommended sequence, with the eval harness measuring every step:

  1. Eval harness + baseline — committed on the branch. Measure today's single-run recall, union recall over N runs, and stability before touching the pipeline.
    The union-vs-single-run gap is the number the redesign must close.
  2. Approach B core — parallel cells, per-cell timeouts, checklist output, K-sample ensemble, voting, verifier. No schema or API changes.
    Highest expected recall win; tune K and the agreement threshold against the harness.
  3. Rule enrichment + routing — offline classification into mechanical / lexical / semantic with window or document scope; chunked scanning for window-scoped rules.
  4. Approach C for mechanical rules — trigger specs drafted offline by LLM, human-reviewed, executed by a safe interpreter; judge calls on the small model.
  5. New streaming contract — stage-aware progress and confidence-tagged, never-retracted violations; coordinated with the frontend redesign.

Your question

Can the regex hybrid be robust? Yes — if the regex never decides

The two number rules show exactly why a naive rule-based checker fails: «Kurze Zahlen im Fliesstext ausschreiben» demands words for digits up to twelve — unless a Sonderregel applies (Masse, Geldbeträge, Fristen) or its sibling «Mehrere Zahlen im gleichen Zusammenhang in Ziffern» inverts the verdict for comparisons. No regex can hold that judgment. The robust split is trigger–judge:

deterministic trigger
100% recall, finds every candidate span → LLM judge
sentence context + rule + sibling rules: violation or exception? → violation (attributed to the right rule)
or dropped as exception
  • The trigger is a recall device, not a verdict. It fires on surface patterns — a digit 0–12 in running text, a sentence mixing Zahlwörter and Ziffern, \d{1,2}:\d{2}, a straight quote. Deterministic, so the LLM's first-hit-only failure mode is gone for these rules: every occurrence becomes a candidate.
  • The judge is a precision device. One short, focused call per candidate: the sentence (±1 sentence of context), the triggering rule and the sibling rules and Sonderregeln its checker spec declares as interacting, and a constrained question — violation, exception, or violation of a sibling rule? That is a task a small model answers reliably, unlike “scan this page exhaustively.”
  • Rules without exceptions skip the judge. «Doppel-s statt Eszett (ß)» declares decides: true — every ß is a violation, no call needed.

«Es wurden 3 Eingaben gemacht.»

Trigger: digit ≤ 12 in running text → fires on «3». Judge: no comparison in the sentence, no Mass/Geld/Frist context → violation of «Kurze Zahlen im Fliesstext ausschreiben», proposal «drei».

«Die Frist beträgt sieben Tage, bei Verträgen 14 Tage.»

Trigger: mixed-usage parser sees Zahlwort «sieben» and Ziffer «14» in one sentence → fires. Judge: the two numbers are compared, so digits are correct here — the digit «14» is fine, and the finding is attributed to the sibling rule instead: violation of «Mehrere Zahlen im gleichen Zusammenhang in Ziffern» on «sieben», proposal «7». A regex-decides checker would have flagged nothing here (14 > 12) or the wrong thing; a pure LLM pass often misses it entirely.

«Die Gebühr beträgt 5 Franken.»

Trigger fires on «5». Judge: Geldbetrag → Sonderregel applies → dropped as exception. (The nearby rule «Geldbeträge mit Währungseinheit vor dem Betrag» is a separate trigger and still fires on «5 Franken».)

Concretely, the checker spec lives next to the rule (additive schema, staged and human-reviewed like the extracted rules themselves):

"checker": {
  "type": "regex",                      // or "number_words" parser
  "pattern": "\\b([0-9]|1[0-2])\\b",
  "decides": false,                     // false → every hit goes to the judge
  "interacts_with": [
    "Mehrere Zahlen im gleichen Zusammenhang in Ziffern",
    "Masse, Gewichte und Währungen mit abgekürzter Einheit in Ziffern",
    "Geldbeträge mit Währungseinheit vor dem Betrag"
  ],
  "exceptions_hint": "Sonderregeln: Masse, Geldbeträge, Fristen, Vergleiche"
}

Cost stays trivial: a typical page triggers a handful of candidates, each one short judge call on the small model — far cheaper than asking Gemma to re-scan the page per rule, and immune to it losing count.

Measurement

Advisor eval — documentation

The harness ships on the branch and makes detection rate a measured number before any pipeline change. Four parts:

  • evals/advisor/cases/*.json — 11 hand-labeled seed cases (ground truth)
  • src/text_mate_tools/advisor_eval/ — case models and scoring (pure, unit-tested, no LLM needed)
  • src/text_mate_tools/run_advisor_eval.py — drives the real AdvisorService and reports
  • src/text_mate_tools/generate_eval_cases.py — LLM-assisted case generator, staging + human review

Running it

# from the repository root, with the backend's .env
uv run --env-file .env src/text_mate_tools/run_advisor_eval.py            # single pass
uv run --env-file .env src/text_mate_tools/run_advisor_eval.py --runs 5   # stability + union recall
uv run --env-file .env src/text_mate_tools/run_advisor_eval.py --case-id bk-guillemets-multi --json-out results.json

# generate more cases (writes to staging/evals for mandatory review)
uv run --env-file .env src/text_mate_tools/generate_eval_cases.py --collection bundeskanzlei --max-cases 5

# scoring unit tests (no LLM required)
uv run pytest tests/test_advisor_eval_scoring.py

Case format

{
  "id": "bk-uhrzeit-double",
  "description": "Same violating substring twice — probes multi-occurrence detection.",
  "collections": ["bundeskanzlei"],
  "text": "Die Anhörung beginnt um 9:30 Uhr im Saal drei. Die zweite Sitzung beginnt um 9:30 Uhr …",
  "expected": [
    { "rule_name": "Uhrzeit mit Punkt in der 24-Stunden-Zählung", "source": "9:30", "occurrence": 1 },
    { "rule_name": "Uhrzeit mit Punkt in der 24-Stunden-Zählung", "source": "9:30", "occurrence": 2 }
  ]
}

source must be an exact substring of text; occurrence selects the n-th hit when it repeats; alt_rule_names accepts sibling attributions where rules legitimately overlap («Kurze, einfach gebaute Sätze» vs «Ein Gedanke pro Satz»). The runner fail-fasts on authoring errors: unknown rule names or snippets that don't resolve.

Scoring semantics

Match
Greedy one-to-one: a prediction matches an expected violation when the rule name matches (exactly or via alt_rule_names) and the character spans overlap. A second prediction on an already-matched expected counts as a duplicate, not a false positive.
Rule confusion
Unmatched predictions are re-checked by span alone: right text span, wrong rule cited. Reported separately — it distinguishes “didn't see it” from “saw it, misattributed it”, which need different fixes.
Recall / precision / F1
Per case, per rule, and overall (micro). Clean negative cases (empty expected) measure the false-positive floor.
Union recall (--runs N)
Recall counting an expected violation as found if any of the N runs found it. Union recall − mean single-run recall = the ensemble headroom — the direct measurement of the “run it again, find more” effect, and the primary gap approach B closes.
Stability (--runs N)
Mean pairwise Jaccard similarity of the found-violation sets across runs. 1.0 = every run finds the same things.

Growing the set

The generator seeds one violation per rule into a realistic Behördentext and emits the labels alongside; every generated case is machine-validated (labels must resolve in the text) and then must be human-reviewed in staging/evals before promotion — the same trust model as the rule-extraction pipeline. Real labeled texts from the editorial team can be added in the same JSON format at any time.
